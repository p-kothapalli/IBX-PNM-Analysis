Rollup Precedence & Chain

PAR form / PDA action creates or terminates a PRM_InfoCodeAssignment__c record. The ICA trigger then fires one queueable per transaction — PRM_ConciergeProviderRollupQueueable — which rolls up in this order:

  1. 1. Account → rollupAccounts() sets Account.PRM_IsConciergeProvider__c = (active Account-level "Concierge Provider" ICA exists today).
  2. 2. HPF (PPL) → rollupHPFs() sets HealthcarePractitionerFacility.PRM_IsConciergeProvider__c = (active HCPF-level "Concierge Provider" ICA exists today).
  3. 3. Practice Location → rollupHCFs() delegates to PRM_ConciergeRollupHelper.evaluateSync(), which applies the 100% rule at the actual ICA transition date (not System.today()) and then either creates / reactivates / date-syncs / terminates the Location-level ICA and flips HealthcareFacility.PRM_IsConciergeProvider__c accordingly.

Independent path — HPF trigger: PRM_HCPFTriggerHelper.handleConciergeRollup also fires whenever an HPF is inserted, updated, or deleted (a practitioner joining or leaving a location can break the 100% rule) and enqueues the Location-level evaluation for the affected facility.
Independent path — Account trigger: PRM_AccountTriggerHelper.handleConciergeRollup fires only when Account.PRM_IsConciergeProvider__c flips true → false; it runs in terminateOnly mode — it will terminate a Location-level ICA if the rule breaks, but it will never auto-create one.

Dependency Order (why the levels must be built bottom-up)

Practitioner ICA → must exist & be active before HCPF (PPL) ICA → must exist for every active PCP/Dual at the location before Location ICA can auto-create.
Key takeaway. The Practitioner flag is the foundation, the HCPF flag is the per-location fact, and the Location flag is a strict AND of every active practitioner at that location. Break any link at the lower levels — a Specialist joins, a PPL ICA is terminated, or the Account flag flips off — and the Location-level ICA auto-terminates the same day.
