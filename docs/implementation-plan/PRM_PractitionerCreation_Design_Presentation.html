Practitioner Creation — Architecture Overview

A reusable, metadata-driven asynchronous engine that onboards large practitioner rosters reliably — bulk-first, idempotent, and resumable — while the existing intake experience continues to run.

Layered Design High-Level Architecture Process Flow
2.1

Layered Design (HLD)

Clear separation of concerns. Only the top two layers are built per intake form; everything below is shared platform that new forms reuse as-is.

L0 · TransportEntry & validation
LWC (JSON/CSV upload) → Apex controller — validate synchronously → PRM_CaseService creates Case Managers → insert PRM_AsyncJob__c → call start(jobId) → return. Legacy OmniScript/IP coexists.
Per form
L1 · Batch classesOrchestration
Four concrete Database.Batchable classes; each wraps its domain service(s) and runs as one stage of the chain.
Per form
L2 · Domain servicesPRM_*Service
Build records + one bulk DML per object type; SOQL-free; carry state via the params / response map.
Shared
L3 · SelectorsPRM_*Selector
All SOQL — bulk-safe, typed, zero DML.
Shared
L4 · UtilitiesCross-cutting helpers
PRM_FormSubUtility (NameNormalize, recordTypeId, computeHcfExternalId, cmaFieldSets) + abstract PRM_ServiceBase.
Shared
Async engineGeneric control plane
PRM_AsyncJob__c → PRM_AsyncOrchestrator.start(jobId) → PRM_AsyncJobRecords__c (per practitioner) + PRM_AsyncJobDetails__c (per stage) → invokes the named batch classes (sequenced, halt-on-failure); dead-letter queue, notifications & cleanup.
Shared
Why it matters: a new onboarding form contributes only a payload/validator and its batch classes — the services, selectors, utilities and async engine are reused, keeping delivery fast and behavior consistent.
