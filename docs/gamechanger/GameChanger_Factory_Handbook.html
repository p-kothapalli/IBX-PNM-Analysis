02

How A Job Moves Through

The GameChangerFactory

You would expect the pipeline to call a model API for each station. It does not. It prints a job card per station and stops.

1. Three phases, with a human step in the middle
PHASE 1 · DAY SHIFT

Context assembly — a CLI command. Deterministic. No model involved.

It prints the job cards and hangs them up.

./scripts/run-production.sh
 --feature <KEY>
 --story-keys <S1>,<S2>
 --phase context-assembly
 --runs-dir ../runs

Writes:
cursor-tasks/00-intake.task.json … one per station, plus cursor-completion-manifest.json

PHASE 2 · NIGHT SHIFT

Generation — and there is no command. You open the workspace in Cursor and its agent works the cards.

  • Read <stage>.task.json — prompts + hints
  • Run every pendingVerifications query before writing a field claim
  • Write the note to the card's expectedOutputPath

"For v1, Cursor AI is the only supported generation runtime." · "No API-key fallback is supported."

PHASE 3 · DAY SHIFT

Extraction — a CLI command. Collects the notes, refuses the blank ones, closes the job.

./scripts/run-production.sh
 --feature <KEY>
 --story-keys <S1>,<S2>
 --phase extract-only
 --runs-dir ../runs

Writes:
story-extraction-packet.json execution-manifest.json

2. WHAT'S ON A JOB CARD

{ stageId · storyKey · featureKey
  expectedOutputPath
  systemPrompt · userPrompt
  contextHints: { priorArtifacts,
    kpBundlePath, runsDir, storyRunDir,
    pendingVerifications[] }
  createdAt }

Where paths disagree between layers, the card's expectedOutputPath is authoritative.

3. CHECKPOINT AFTER EACH PHASE
  • After 1: the manifest lists one pending task per station per story. An empty pending list means nothing was scheduled — usually a story key that doesn't resolve.
  • After 2: every station file exists and none still holds its placeholder marker.
  • After 3: an extraction packet exists per story and the manifest is updated.

A station sitting at cursor_pending is waiting, not broken. It means the card is written and Phase 2 hasn't reached it yet. A placeholder that survives into Phase 3, though, fails extraction — go back to Cursor for that one card. Phase 1 does not need re-running.

WHERE THE ANALOGY BREAKS  ①

A real factory station runs itself. These don't. The pipeline is deliberately built so the generating agent has live tool access — it can run SOQL, retrieve metadata and read the repo while it writes.

A detached model call could not verify its own claims, which would defeat the whole verification ladder. So budget the editor time: this is not a fire-and-forget batch job.

4. WORTH KNOWING
Knowledge snapshot cache-hit< 4 h
Older than thatdelta refresh
Ignore the cache--force-full-fetch
Preflight modealways strict
Story filterREADY | ALL
Max stories per run50

Strict preflight refuses to proceed on warnings. That is the intent, not a bug.

The factory prints the cards and stops. You are Phase 2 —
and that is the design, because verification needs live hands on the real org.

03

The House Rule

The GameChangerFactory

If the drawing and the real car disagree, the real car wins.

Not recency. Not specificity. And certainly not whichever one the model found more convincing.

1. The five shelves — what a source is allowed to say
0authoritative Live org metadata and SOQL results. Wins everything. Infinity
1scoping Contract / statement-of-work packs. Bounds what's in scope — never states a platform fact. 800
2guidance Architecture standards and reference docs.1200
3persona Role profiles shaping tone and audience.600
4background Narrative colour. Never decisive.400

Right-hand column is the per-pack token cap. Lower rank number = higher authority. Everything below authoritative competes for one shared budget of 4000; authoritative packs are admitted regardless of what's left.

2. THE TAPE MEASURE — four rungs, in order
1The warehouse snapshot. Check the cached org bundle → label it [Verified: KP Bundle]
2Go and look. Run live SOQL against the read-only org — FieldDefinition, EntityDefinition
3Ask the paperwork. The ticket system, then the wiki → [Verified: Jira]
4Admit it. [Inferred: UNVERIFIED] — and raise an open question if anything downstream depends on it

There is no fifth option. Every claim is traceable to something outside the model, or explicitly admitted as unverified.

GOLDEN RULE

You may only claim a part exists
if you went and looked.

3. THE CARD HANDS YOU THE QUERY

The factory pre-computes the misses. Goods-In scans the story text for API names, diffs them against the warehouse snapshot, and emits ready-to-run SOQL as pendingVerifications on the job card.

The agent is handed the exact query it needs to prove the field is real. Skipping it is a choice, not an accident.

0.0
4. PACKS DECAY

Freshness falls linearly over 24 h, then resolves to nothing — not "a bit less". A two-week-old planning note cannot quietly overrule today's org.

TWO VOCABULARIES — DON'T CONFUSE THEM

The five-shelf ladder above governs context packs. A second registry uses a wider, different enum that adds high-trust advisory experimental.

They are not the same enum. Do not map one onto the other by name.

5. THE TELL

If a station cites a field you don't recognise, look for the [Inferred: UNVERIFIED] label.

If it isn't there, the agent skipped verification. Check the snapshot is fresh and the org connection is live, then re-run that one station.

Precedence decides, not persuasion. Live org metadata outranks every document
in the building — including the ones an earlier station wrote.

THE STATION, IN ONE LINE

Marks everything up in red pen — then decides whether the job is allowed to move on at all.

WHAT LANDS IN THE IN-TRAY
  • Artifacts 00 through 03
  • Any implementation that already exists
  • The platform rule set

A missing artifact is itself a critical finding.

THE EXAMPLE the job we follow: PRM_CaseDataManagerService
In:
Everything written so far, plus whatever implementation exists.
Does:
Checks one bulk write per object type, sharing enforced, field-level security honoured, no hardcoded record identifiers — and numbers each finding with a severity.
Out:
04-code-review.md — a pass / fail / pending checklist and an explicit may-this-proceed decision.
WHAT IT ACTUALLY DOES
  1. Load artifacts 00–03. If one is missing, that absence is logged as critical rather than worked around.
  2. Review against the platform rule set: bulkification, governor limits, sharing and field-level security, error handling, trigger patterns.
  3. Emit numbered findings with severities, plus a checklist of at least seven named checks.
  4. Apply the gate — no critical or high findings, proceed; a critical finding blocks and marks the run degraded; missing or inadequate test design sends the work back to 03-tdd.
  5. Write prioritised recommendations and hand off to the Assembly Bay.

THE STATION, IN ONE LINE

The only station that touches metal — and it only ever test-fits, never ships.

WHAT LANDS IN THE IN-TRAY
  • The architecture decisions
  • The red-pen findings — as one fix backlog
  • Deploy and test tooling, plus the org
THE EXAMPLE the job we follow: PRM_CaseDataManagerService
In:
The decision records plus the red-pen findings, treated as a single backlog.
Does:
Generates PRM_CaseDataManagerService and its test class, runs a check-only deploy against the one writable org, then classifies each error by kind and applies the minimal fix.
Out:
05-build-fix.md — the metadata, the deploy result, and honest deploy and test counts.
WHAT IT ACTUALLY DOES
  1. Treat the decision records and review findings as one fix backlog, not two lists.
  2. Generate the metadata — objects, fields, platform code.
  3. Classify every error by kind — compile, metadata, dependency, governor limit, test failure. The remedy differs by class, and guessing wastes a deploy cycle.
  4. Apply the minimal fix, re-run the check-only deploy, and confirm that specific error is gone before moving on.
  5. Run the validation checklist; record real deploy and test counts.
  6. On rework, patch in place — never regenerate. Escalate after three identical failures rather than looping.
THE CUPBOARD IS LOCKED

Exactly one org alias is write-allowed. Every other alias is look-don't-touch, enforced by a shell hook that inspects the command before it runs and exits with a refusal.

Deploys are check-only. This bay validates that the parts fit; it is not despatch.

WHAT IT ACTUALLY DOES

  2. Identify the critical flows: happy path, error path, boundary, bulk, permissions.
  3. Lead with the readiness verdict — eight-plus dimensions each rated, plus one overall line. Mandatory, and it goes at the top so nobody has to hunt for it.
  4. Maintain a blocker registry of every scenario not run or blocked — or state explicitly that there are none.
  5. Execute what can be executed and mark the rest NOT RUN. A fabricated pass is the exact failure this station exists to prevent.
  6. Fill the execution matrix with criterion links and hand off to the Locks Bench.
THE READINESS TABLE — WHY IT'S FIRST

A rated table forces a per-dimension judgement. Burying a weak dimension inside prose is easy; leaving it amber at the top of the page is not.

ACCEPT — good, carry on.

3. HOW MANY SECOND CHANCES?

One, by default. The refine cap is 1 in the running code — though the README says 2 and some command paths pass 3. Check the value you are actually running with.

At the cap the loop stops and returns the last verdict unchanged — which may well still be REFINE_AGAIN.

The documentation says a station is promoted to ACCEPT_WITH_CAVEATS when it hits the cap. The code does not do this. Don't rely on it.

4. THE DOMAIN CHECK

One extra rule fires regardless of station: if the work touches regulated clinical data and the artifact never mentions the governing privacy standard, that is critical on its own.

WHERE THE ANALOGY BREAKS  ②

The belt doesn't actually stop. Each station's rules declare a rework trigger — the station it would send work back to.

Nothing in the running code reads those declarations. Refinement happens within a station's own loop; there is no automatic reverse conveyor. Backwards movement is a human decision.

Eight inspectors, four verdicts, one refine by default. Two of them are full tier —
the blueprint and the locks, which is where a mistake costs the most.

3. THE LOCKED TOOL CUPBOARD

Exactly one org alias is write-allowed. Every other alias in the registry is read-only, and the enforcement is not a convention — it's a hook.

If the registry can't be read, the guard falls back to a hardcoded list and still protects the known production aliases. It fails closed, not open.

READ THIS BEFORE YOUR FIRST RUN. The org registry ships pre-populated with placeholder orgs from another engagement, and the write guard reads that same file at runtime.

Replace it from the template before the first run — otherwise you are protecting somebody else's org names and not yours.

TWO KINDS OF NO

The inspectors say no with judgement. They read an artifact, score it, and can be argued with across a refine cycle.

The rule book and the cupboard say no with arithmetic. A threshold is a threshold and a blocked alias is a blocked alias. Neither negotiates.

Which one you've hit changes what you do next. An inspector returning REFINE_AGAIN is a conversation — improve the artifact and it may accept. A policy threshold or a blocked alias is a fact: you either change the underlying condition, or you record a properly justified waiver. Arguing with it in the artifact will not work.

Judgement is for the inspectors. The rule book only does arithmetic —
and the cupboard door only does locked or unlocked.

THE LIBRARIAN

Read-only everywhere, and it never blocks anything. It fetches from the ticket system, the wiki, the org and the repository.

The trap: when a source fails it sets a degraded flag and carries on. A bundle can look present while being nearly empty. Check the flag, not just the file.

THE AUDITOR

Asks whether the folder is complete before anyone is allowed to score it. Three outcomes: pass, review, escalate.

If the bundle is missing entirely, that is a critical gap and an immediate escalation — not a low score.

THE OLD SCORER — DEPRECATED

A four-part weighted score:

Alignment.30
Process health.25
Evidence completeness.25
Risk readiness.20

Approve at 0.8, defer at 0.6. Marked deprecated in favour of the eight-dimension model. Both still appear in the codebase — the eight-dimension card is the canonical one.

THE ROUTER

Runs the rule book and combines the results on a worst-wins basis.

One escalate escalates everything. Not an average, not a majority — the single worst outcome sets the route for the whole run.

It also validates waivers, so an exception has to be properly justified rather than merely asserted.

THE STAPLER

Assembles the final folder for the people who sign things — one human-readable and one machine-readable, written side by side.

Filenames matter here: boardpacket-v2.md and boardpacket-v2.json. Not board-packet.md — the hyphenated name appears in some documentation and does not match what the code writes.

THE ORDER IS LOAD-BEARING

You cannot score what you haven't audited, and you cannot audit what nobody gathered.

Which is why a quiet degraded flag at step one propagates all the way to the signature at step five.

Worst-wins, all the way down. One escalation escalates the whole run —
and a degraded fetch at the first desk is felt at the last.

The one thing not to do

Do not hand-edit a bad artifact to make the run go green. The whole value of ten stations is that a failure has an address. Editing the note by hand deletes the address and keeps the fault.

THE DIAGNOSTIC ORDER
  1. Which pigeonhole is empty or thin?
  2. What did that station's inspector say?
  3. Was that station's input complete?
  4. Only then: is the content actually wrong?

Most jams resolve at step 3.

REMEMBER WHAT THE REFINE LOOP CAN AND CANNOT DO

It can improve an artifact whose inputs were sound — that's exactly the loop it was built for.

It cannot repair a station whose input was wrong, and there is no automatic reverse conveyor to send work back upstream. That move is yours to make.

When a station complains, suspect its input before its output.
Three of the seven jams above are fixed at a completely different station.

WHAT THE FACTORY IS ACTUALLY FOR

Not that twenty-three agents beat one. That a failure gets an address.

One prompt gives you one blob, and nothing in it ever "failed" — you just get a worse answer with no way to say where it went wrong. Ten stations give you ten reviewable decisions, each with a named owner, a named rule, and a note in a pigeonhole.

Everything else on the floor — the tape measure, the inspectors, the locked cupboard, the mechanic who can't sign his own work — exists to protect that one property.

YOUR FIRST RUN, IN ORDER
  1. Replace the org registry from the template. Nothing else matters until this is done.
  2. Run Phase 1. Confirm the manifest lists one task per station per story — an empty pending list means nothing was scheduled.
  3. Open the workspace in the editor and work each card. Run the supplied verification queries rather than assuming a field exists.
  4. Run Phase 3. Confirm no placeholder survived into the extraction packet.
  5. Read the ten notes in order. Start at the first thin one — and check its input before its output.
THE THREE TO REMEMBER
  • You may only claim a part exists if you went and looked.
  • You are Phase 2. Budget the editor time.
  • Replace the org registry first.

Every identifier, threshold and number in these 22 pages is copied from the grounded system write-up, which was itself read out of the source tree — the execution contracts, the station rule files, the policy definitions and the agent implementations.

Nothing here was inferred to fill a gap. Where the code and the docs disagreed, that disagreement became a row in the table above rather than a quiet choice.

The point was never the twenty-three agents.
